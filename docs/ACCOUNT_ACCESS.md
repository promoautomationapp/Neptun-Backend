# Invitation-only team access

Neptun Broshura uses database-backed sessions and tenant-scoped memberships. Existing staff and PM accounts remain available. There is no public sign-up endpoint. Administrators can invite staff, PMs and other Neptun administrators, edit names/roles, resend pending invitations and deactivate/reactivate verified users. Support superadmins are visible only to other superadmins. Neptun users do not receive support identities in team lists, mention pickers, document activity or collaboration presence. Support activity uses a generic workspace label while the original audit identity remains stored. At least one active Neptun admin must remain. Support accounts are added only by an operator-controlled bootstrap, never by the admin invitation API.

## Email setup

Email credentials belong only in the backend's private environment or deployment secret manager. Keep local `.env` permissions at `600`; do not put credentials in the frontend or commit them. Keep `MAIL_DRIVER=disabled` during setup so configuring credentials cannot dispatch the durable outbox accidentally.

Two delivery transports are available:

- Resend: set `MAIL_DRIVER=resend`, `RESEND_API_KEY` and a sender verified with Resend.
- SMTP: set `MAIL_DRIVER=smtp`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER` and `SMTP_PASS`. Port 465 requires `SMTP_SECURE=true` for TLS from connection start. Port 587 normally uses `SMTP_SECURE=false` with mandatory STARTTLS. Certificate validation is always enabled. For Gmail, use `smtp.gmail.com` with the full Gmail login address and its app password. Remove spaces shown between groups in a Google app password when storing it. Do not use a normal account password.

Set `MAIL_FROM` to one verified mailbox, optionally with a display name (`Neptun Campaign Studio <sender@example.com>`). SMTP authentication does not prove ownership or deliverability of a different From address. A custom address used through Gmail must be configured and confirmed as a “Send mail as” address; Gmail may still expose the authenticating Gmail account. For a branded domain sender, use a provider that authenticates that domain with aligned SPF/DKIM and configure DMARC. A Gmail app password alone cannot configure a custom domain or its DNS. Do not invent DNS records or enable an unverified From address. [Google's alias instructions](https://support.google.com/mail/answer/22370) and [sender authentication guidelines](https://support.google.com/mail/answer/81126) describe the provider requirements. These measures improve delivery; no provider or email design can guarantee inbox placement.

Run `npx tsx scripts/verify-email.ts` to check SMTP TLS and authentication without sending a message. This works while delivery is disabled. It does not check that a custom sender alias has been confirmed. Before enabling a driver, inspect pending outbox metadata and ensure `PUBLIC_APP_URL` points to the actual public HTTPS frontend, so invitation/reset links work for recipients. A successful authentication check is not an end-to-end delivery test.

Set `MAIL_BRAND_NAME` and an optional public HTTPS `MAIL_LOGO_URL` to your support team's approved branding. An authenticated/private asset URL will not work in email clients. The email renderer includes a readable wordmark when no public logo is configured, and HTML and plain-text versions. It escapes user-provided content, includes clear expiry instructions and readable links/codes, and does not include marketing, tracking pixels or attachments. No provider credentials or guessed administrator addresses are committed.

Set `BOOTSTRAP_SUPPORT_EMAIL` and `BOOTSTRAP_ADMIN_EMAIL` to the approved, distinct addresses and run `npx tsx scripts/bootstrap-admins.ts` after migrations. It prepares the two organization memberships and queues invitations, preserving existing passwords. Repeated runs preserve active accounts and unexpired invitations. The server's email dispatcher must be running to deliver the queued invitations. No default password is assigned for new invited accounts. The development seed script remains separate and requires its own `SEED_DEFAULT_PASSWORD` only when run.

For a new workspace whose initial administrators need password login before a sender is configured, an operator can run `npm run accounts:initial -- --credentials-file=/absolute/private/path` with the two approved bootstrap addresses. This creates only the initial support superadmin and Neptun admin, scoped to Neptun, with independent random passwords hashed using Argon2id. These two default accounts use regular password login without a forced first-login password change. The identifier approval is recorded as an operator action; no email is sent. Other users retain the invitation and working-email verification flow. A Neptun administrator cannot modify the protected support account.

The password credentials are written only to the specified new local file with mode `0600`; passwords never appear in command output or audit records. The file must stay outside Git. An existing credential file or existing administrators cause the command to stop without resetting passwords or changing roles. Email recovery still requires a working mailbox and configured sender. Existing workspaces should use their account management and invitation flow.

Invitation links use `/account/invitation?token=...` and expire after 48 hours. They identify the invited account; users choose a password, then verify a six-digit emailed code that expires after 10 minutes. The password is stored as a pending Argon2 hash until verification. Failed code attempts persist and are limited; resends rotate the code. Password reset links use `/account/reset-password?token=...`, expire after 30 minutes and require another emailed code. Public forgot-password responses are identical for existing and unknown addresses. Password changes require the current password. Completed password changes/resets revoke all previous sessions and queue a notice email. Role changes and deactivation revoke that organization's sessions.

## Delivery and operations

Account emails are committed to an encrypted database outbox in the same transaction as the account change. Tokens/code payloads are AES-256-GCM encrypted using a key derived from `SESSION_SECRET`; the token/code columns themselves store HMAC digests. Keep that secret stable, protected and backed up. API instances claim outbox messages with database locks every two seconds. Resend requests use the outbox ID as an idempotency key. SMTP uses a stable Message-ID for each outbox row; this supports tracing but cannot guarantee exactly-once delivery after an ambiguous connection timeout. Transient failures retry up to six times with a two-minute delay. Permanent provider rejections stop retrying. Provider failures are stored as sanitized categories, never raw SMTP responses. Verification emails are not delivered after their code expires. New queued account links/codes replace older pending account messages for that recipient and kind; independent mention notification emails are retained. Sent payloads are erased; failed-message metadata is available in `email_outbox`.

The two provisioned default administrators retain their verified password access without an invitation or a new email verification. Email configuration affects new invitations and password recovery, not these existing logins.

An unconfigured sender is visible as `emailConfigured:false` in the administrator API; invitation creation/resending and code delivery fail explicitly with 503. Forgot-password retains its generic response, and cannot send until email is configured. Password-change notices remain durable in the outbox until a sender is configured. API success for a code request means the message is queued, not that the recipient's mail server has delivered it.

Inspect delivery with `SELECT kind,status,attempts,created_at,sent_at,error FROM email_outbox ORDER BY created_at DESC`. Do not log decrypted payloads or tokens. Administrator mutations and password changes are recorded in `account_audit`; public endpoints use database-backed rate limits. The development and automated tests use a disabled sender; no real emails are sent.

Brochure review notifications and mention delivery are described in [Review notifications](NOTIFICATIONS.md).

## Staff and PM workspace controls

Invitations and user updates accept an optional `access` object. The team editor keeps these controls collapsed by default. Choose usual role access or custom access, then use switches for disabling brochures, opening social posts, and browsing the product catalog. Catalog access can cover all categories or selected branches from the workspace's searchable category tree; selecting a parent includes all its descendants. Existing shared brochures keep their saved product snapshots and remain visible.

The object contains `mode` (`default` or `custom`), `canDisableBrochures`, `canViewSocialPosts`, `canViewCatalog`, and `catalogCategoryPaths` (`null` for all branches, otherwise at most 100 canonical paths). Missing access, `null`, and default mode preserve normal role behavior. Admins and superadmins retain full workspace access. Controls cannot grant administrative or review privileges beyond the user's role.

Restrictions are stored on the organization membership, validated against that workspace's catalog/source paths, and returned in managed-user and session responses. Every authenticated request reads current membership permissions. Catalog list, batch/code lookup, facets and brand endpoints enforce the same category scope; direct social reads/writes and brochure disable actions enforce their feature permission. Scope filters use bound SQL values and escape wildcard characters. A malformed custom restriction fails closed.

Permission updates are recorded in `account_audit` and normal request activity with the administrator, time, result and request metadata. The interface refreshes sessions on focus/visibility and every minute while visible, removes newly forbidden navigation/actions, cancels catalog loads, and clears restricted catalog views without remounting the workspace shell. Temporary network failures retain the open workspace; revoked/disabled sessions return to sign-in. Role/status changes retain the existing session-revocation behavior. Verified disabled users can be re-enabled without SMTP or another email verification; unverified cancelled invitations still require a fresh invitation.
